# AI 辅助二次开发工作规范

适用对象：从产品经理、项目经理、业务负责人转向 AI 辅助编码的人。

适用场景：开源项目二开、内部系统改造、SaaS 原型开发、后台管理系统、数据标注平台、AI 应用平台等。

本文不是某一个项目的安装说明，而是一套可迁移的方法：如何用 AI 快速、准确、专业地理解代码、提出需求、拆分任务、修改系统、验证结果，并逐步形成自己的开发能力。

---

## 1. 核心判断

AI 编码不是“让 AI 替你写代码”，而是把你从“亲手敲每一行代码”转为“指挥一个能读代码、能改代码、能跑验证的工程助手”。

产品经理的优势不是少，而是很大：

- 你更容易判断需求是否成立。
- 你更容易识别用户流程、业务边界和优先级。
- 你更容易把改动拆成可验收任务。
- 你更容易判断“功能做出来”和“产品可用”之间的差距。

但短板也很明确：

- 容易低估工程依赖、数据结构、权限、安全、部署带来的复杂度。
- 容易只看页面，不看后端、数据库、任务队列、文件存储。
- 容易让 AI 一次改太多，导致问题难以定位。
- 容易相信 AI 的解释，而不是用运行、日志、测试和代码证据验证。

所以你的工作方法要从一开始就按“产品判断 + 工程证据 + 小步验证”来设计。

---

## 2. 三条总原则

### 2.1 先理解，再改动

任何二开项目，先让 AI 帮你完成四张地图：

1. 项目结构地图：前端、后端、数据库、部署、配置分别在哪。
2. 业务流程地图：登录、建项目、导入数据、标注、审核、导出分别走哪些模块。
3. 数据模型地图：核心表、核心对象、对象关系、状态流转。
4. 运行验证地图：如何启动、如何看日志、如何跑测试、如何判断改动成功。

没有这四张地图，不进入大改。

### 2.2 小步快跑，每次只改一个闭环

一次任务只做一个可验收闭环：

- 一个页面文案调整。
- 一个字段新增。
- 一个按钮行为变化。
- 一个接口返回新增字段。
- 一个权限判断调整。
- 一个导出格式变化。

不要一上来就说“重构整个标注流程”“加一套权限体系”“做一个全新的数据集管理平台”。这种需求要先拆成路线图。

### 2.3 AI 产出必须被验证

AI 写出来不算完成，满足下面至少一项才算完成：

- 页面能访问，交互能走通。
- 接口能请求成功。
- 数据库迁移能执行。
- 单元测试或端到端测试通过。
- Docker 镜像能构建并启动。
- 日志没有关键错误。
- 旧功能没有被明显破坏。

## 3. 推荐工具体系

工具不要贪多，先搭一套稳定组合。

### 3.1 主力编码代理

用于读仓库、改代码、运行命令、修复报错。

可选：

- Codex：适合在本地项目里读代码、改文件、跑验证，适合你现在这种“我有一个本地源码项目，要边学边二开”的场景。
- Cursor：适合在编辑器里边看代码边对话，支持项目级上下文、规则、Agent、MCP、CLI 等能力。
- GitHub Copilot：适合 VS Code/JetBrains/GitHub 工作流，官方文档覆盖 Chat、Agent、Code Review、自定义指令、MCP、云端/本地沙盒等能力。

建议：现阶段不要纠结“哪个最强”，先固定一个主力代理，把工作流程练熟。

### 3.2 代码审查工具

用于在提交前发现明显问题。

可选：

- CodeRabbit：偏 PR 审查、实现计划、IDE/CLI 实时反馈，适合团队协作和 Pull Request 流程。
- GitHub Copilot Code Review：适合已经在 GitHub 上管理代码的项目。

建议：个人二开早期可以先让 Codex 做本地 review；准备形成长期项目后，再接入 PR 审查工具。

### 3.3 编辑器和基础插件

推荐基础组合：

- VS Code 或 Cursor。
- GitLens：看提交历史、文件变更、代码作者。
- Docker 插件：看容器、镜像、日志。
- PostgreSQL/MySQL 数据库插件：查看表结构和数据。
- REST Client 或 Bruno/Postman：调接口。
- Error Lens：在编辑器里突出显示错误。
- Prettier/ESLint/Pylance/Ruff：格式化和静态检查。

注意：插件只是提高效率，不替代基本流程。不要装一堆插件后没有自己的开发规范。

### 3.4 文档和知识库

建议每个二开项目都保留这些文档：

- `docs/project-map.md`：项目地图。
- `docs/dev-runbook.md`：启动、构建、测试、部署手册。
- `docs/change-log.md`：二开改动记录。
- `docs/decision-log.md`：关键技术决策记录。
- `docs/ai-prompts.md`：沉淀好用提示词。

## 4. 两类项目的完整生命周期

你后续会遇到两类项目：

- A 类：基于开源项目二开，例如本次 Label Studio。
- B 类：从 0 到 1 开发，例如自己做一个内部业务系统、AI 工具、管理后台。

两类项目都不是从“写代码”开始，而是从“判断要不要做、怎么做才划算”开始。

### 4.1 总流程图

```text
想法/问题
-> 场景确认
-> 方案选择：二开 / 从零开发 / 采购 / 组合
-> 技术可行性验证
-> 项目结构设计
-> 最小可用版本
-> 功能迭代
-> 测试验收
-> 部署上线
-> 运营维护
-> 复盘沉淀
```

每一步都要有判断标准。没有判断标准，AI 会很勤快地把你带到错误方向上。

### 4.2 第一步：判断问题是否值得做

要回答：

- 谁遇到了问题？
- 现在怎么解决？
- 痛点是效率、成本、质量、合规，还是体验？
- 如果不做，会有什么损失？
- 有没有现成工具能解决？
- 做到什么程度就算有价值？

最好判断：

- 用户真实存在。
- 场景高频或高价值。
- 当前方案明显低效。
- 结果能被验证。
- 第一个版本能在 1-2 周内做出闭环。

危险信号：

- 只有一句“我想做个平台”。
- 用户、场景、数据都不清楚。
- 第一版就想做大而全。
- 没有明确验收方式。

### 4.3 第二步：判断用二开还是从零开发

用二开，适合：

- 开源项目已经覆盖 60% 以上核心流程。
- 你主要是改界面、流程、权限、字段、导出、集成。
- 原项目活跃、有文档、有社区。
- 许可证允许你的使用方式。
- 你能接受原项目的技术栈和架构。

从零开发，适合：

- 开源项目太重，二开成本高于重写。
- 需求很独特，原项目只覆盖一小部分。
- 你需要完全掌控数据模型、权限、部署和 UI。
- 合规、安全、国产化、内网部署等约束很强。
- 只需要一个很小的垂直工具。

采购或低代码，适合：

- 需求通用。
- 内部没有维护能力。
- 时间非常紧。
- 成本比自研更可控。

最好判断：

```text
二开价值 = 已有能力可复用程度 - 理解成本 - 改造成本 - 后续维护成本
```

不要因为“代码已经有了”就默认二开。开源项目越大，理解和维护成本越高。

### 4.4 第三步：技术可行性验证

二开项目要验证：

- 源码能不能跑起来。
- Docker 能不能构建。
- 核心流程能不能走通。
- 想改的功能能不能定位到代码。
- 数据库结构是否能理解。
- 许可证是否允许商用或内部使用。

从零项目要验证：

- 技术栈能否支撑目标功能。
- 核心依赖是否成熟。
- AI 能否稳定生成和维护该技术栈。
- 是否有可部署路径。
- 是否能接入真实数据或模拟数据。

最好判断：

- 先做技术 Spike，不超过 1-2 天。
- Spike 只验证关键风险，不做完整功能。
- 验证结果必须有运行截图、命令、代码位置或测试结果。

### 4.5 第四步：定义 MVP

MVP 不是“简陋版本”，而是“最小可验证业务闭环”。

MVP 必须包含：

- 一个明确用户。
- 一个明确场景。
- 一个输入。
- 一个处理过程。
- 一个输出。
- 一个验收标准。

例如标注平台二开，MVP 不应该是“改造成智能标注平台”，而可以是：

```text
管理员创建项目
-> 上传 10 条文本
-> 标注员完成分类标注
-> 审核员查看结果
-> 导出 CSV
```

最好判断：

- 一个人能在 10 分钟内演示完整流程。
- 流程里没有“以后再说”的关键环节。
- 输出结果能被业务人员看懂。

### 4.6 第五步：设计版本路线

建议按三层规划：

- V0：跑通和验证，不追求漂亮。
- V1：解决核心业务闭环。
- V2：优化效率、权限、统计、自动化。
- V3：规模化、稳定性、安全、运维。

不要把 V3 的东西塞进 V0。

常见 V0 不该做：

- 完整权限体系。
- 大屏和复杂报表。
- 全量数据迁移。
- 多租户。
- 高并发优化。
- 插件市场。

常见 V0 必须做：

- 登录或最小身份识别。
- 核心数据录入。
- 核心处理流程。
- 核心结果输出。
- 最小错误提示。
- 基础数据备份。

## 5. 开源二开完整流程

以 Label Studio 这类项目为例，二开要按 10 个阶段走。

### 阶段 1：资产盘点

要做：

- 确认源码目录。
- 确认当前分支和上游仓库。
- 确认 Docker 镜像、容器、数据目录。
- 确认旧环境是否需要保留。
- 确认许可证。

关键命令：

```bash
git remote -v
git branch --show-current
git status
docker ps
docker images
```

最好判断：

- 能说清“源码在哪里、镜像在哪里、容器在哪里、数据在哪里”。
- 旧环境可恢复。
- 新环境不会覆盖旧数据。

### 阶段 2：运行隔离

要做：

- 新源码版使用独立端口。
- 新源码版使用独立数据目录。
- 不直接连旧生产数据库。
- 记录启动命令。

最好判断：

- 旧版本和源码版能并存。
- 删除测试数据不会影响旧版本。
- 端口冲突、数据挂载都清楚。

### 阶段 3：项目地图

要产出：

- 技术栈地图。
- 目录结构地图。
- 启动流程地图。
- 前后端关系图。
- 数据库表关系初图。

让 AI 输出时要强调“证据”：

```text
每个判断都要给出文件路径或配置依据，不要凭经验猜。
```

最好判断：

- 能定位前端页面。
- 能定位后端接口。
- 能定位数据模型。
- 能定位部署配置。

### 阶段 4：业务流程地图

要画清：

- 登录流程。
- 用户和组织流程。
- 项目创建流程。
- 数据导入流程。
- 标注流程。
- 审核流程。
- 导出流程。

最好判断：

- 每个流程都有入口页面、接口、核心模型、状态变化。
- 能说明数据从页面到数据库再到导出的路径。

### 阶段 5：改造点选择

优先做：

- 低风险 UI 改动。
- 文案、布局、默认配置。
- 导出格式小调整。
- 新增非核心字段。
- 新增只读统计。

暂缓做：

- 权限体系重写。
- 标注数据结构重写。
- 核心状态机重写。
- 大规模前端重构。
- 依赖升级。

最好判断：

- 第一个改动当天能完成。
- 失败后能快速回滚。
- 不影响核心数据。

### 阶段 6：需求转技术方案

每个二开需求都要过这张表：

| 维度 | 要回答 |
| --- | --- |
| 页面 | 哪些页面受影响 |
| 接口 | 哪些 API 受影响 |
| 数据 | 哪些表/字段受影响 |
| 权限 | 哪些角色受影响 |
| 配置 | 是否需要环境变量 |
| 部署 | 是否需要重新构建镜像 |
| 迁移 | 是否需要数据库迁移 |
| 测试 | 怎么证明改对了 |

最好判断：

- AI 能指出修改文件。
- AI 能说明不改哪些地方。
- AI 能给出回滚方式。

### 阶段 7：小步开发

每次只做一类改动：

- 前端展示。
- 后端接口。
- 数据模型。
- 权限判断。
- 导入导出。
- 部署配置。

最好判断：

- 单次改动文件数量可控。
- Git diff 能看懂。
- 每次提交都有清晰目的。

### 阶段 8：验证

至少验证：

- 构建是否成功。
- 页面是否正常。
- 核心流程是否走通。
- 日志是否报错。
- 数据是否正确保存。
- 旧功能是否仍可用。

涉及权限时必须验证：

- 管理员。
- 普通用户。
- 未登录用户。
- 无权限用户。

最好判断：

- 有明确测试账号。
- 有固定测试数据。
- 有固定验收清单。

### 阶段 9：打包部署

要做：

- 构建自定义镜像。
- 固定镜像 tag。
- 固定环境变量。
- 固定数据目录。
- 写部署回滚说明。

镜像命名建议：

```text
my-label-studio:v0.1.0
my-label-studio:v0.1.1
```

不要一直只用 `latest`，否则后面很难知道线上跑的是哪版。

### 阶段 10：维护上游关系

要做：

- 记录基于哪个上游 commit。
- 定期看上游 release。
- 区分本地改动和上游改动。
- 重要改动写 decision log。

最好判断：

- 以后有人接手，也能知道你改了什么、为什么改。
- 上游升级时能评估冲突风险。

## 6. 从 0 到 1 开发完整流程

从零开发不是“让 AI 直接生成一个系统”。正确方式是先定边界，再逐步扩展。

### 阶段 1：问题定义

输出一页纸：

```text
项目名称：
目标用户：
核心场景：
当前痛点：
目标收益：
第一版范围：
不做范围：
验收方式：
```

最好判断：

- 不超过一页。
- 能被非技术人员看懂。
- 有明确不做范围。

### 阶段 2：需求清单

按用户故事写：

```text
作为【角色】，
我希望【完成某事】，
以便【获得价值】。
```

每条需求必须有验收标准：

```text
当……
如果……
那么……
```

最好判断：

- 每条需求可测试。
- 每条需求能排优先级。
- 每条需求能判断是否完成。

### 阶段 3：产品原型

可以先用：

- 手绘草图。
- Figma。
- Excalidraw。
- Markdown 页面说明。
- AI 生成的 HTML 原型。

重点不是漂亮，而是确认：

- 页面有哪些。
- 用户怎么走。
- 数据在哪里出现。
- 操作后状态怎么变。

最好判断：

- 用户流程能从头走到尾。
- 页面数量尽量少。
- 每个按钮都有明确结果。

### 阶段 4：技术选型

默认优先选成熟、常见、AI 支持好的技术栈。

常见选择：

- Web 全栈：Next.js + PostgreSQL。
- 后台管理：React/Vue + FastAPI/Django/NestJS。
- Python 工具型系统：FastAPI + SQLModel/SQLAlchemy。
- 快速内部工具：Streamlit/Gradio。
- 移动端：React Native/Expo。

最好判断：

- 不是最新最炫，而是资料多、问题容易搜、AI 熟悉。
- 部署路径清楚。
- 数据库和权限方案清楚。

### 阶段 5：数据模型

先画实体：

```text
用户
组织
项目
任务
文件
记录
审批
导出
```

再确定关系：

```text
一个组织有多个用户
一个项目有多个任务
一个任务有多条处理记录
```

最好判断：

- 名词稳定。
- 关系简单。
- 状态可枚举。
- 后续报表能从数据里算出来。

### 阶段 6：架构设计

小项目也要有最小架构：

```text
前端页面
-> 后端 API
-> 数据库
-> 文件存储
-> 权限
-> 日志
-> 部署
```

AI 项目还要补：

```text
模型调用
-> Prompt 模板
-> 上下文数据
-> 结果缓存
-> 人工审核
-> 失败兜底
```

最好判断：

- 每层职责清楚。
- 数据流向清楚。
- 出错点有日志。

### 阶段 7：开发计划

按垂直切片开发，而不是按技术层开发。

错误拆法：

```text
先做所有数据库
再做所有接口
再做所有页面
```

推荐拆法：

```text
第一片：登录 -> 创建项目 -> 展示项目列表
第二片：上传数据 -> 生成任务 -> 展示任务
第三片：处理任务 -> 保存结果 -> 导出结果
```

最好判断：

- 每一片都能演示。
- 每一片都能验收。
- 每一片都能独立提交。

### 阶段 8：开发执行

每个任务都按：

```text
需求
-> 方案
-> 修改
-> 验证
-> review
-> 提交
```

让 AI 每次先回答：

- 我要改哪些文件。
- 为什么改这些文件。
- 怎么验证。
- 风险在哪里。

### 阶段 9：测试验收

至少准备：

- 正常路径测试。
- 异常路径测试。
- 空数据测试。
- 权限测试。
- 刷新页面测试。
- 重启服务测试。
- 数据备份恢复测试。

最好判断：

- 不是只测“能不能点”。
- 要测“错了怎么办”。
- 要测“数据还在不在”。

### 阶段 10：上线和运维

上线前确认：

- 环境变量。
- 数据库备份。
- 管理员账号。
- 日志位置。
- 回滚方式。
- 域名和 HTTPS。
- 权限和数据安全。

最好判断：

- 出问题知道看哪里。
- 出问题知道退回哪版。
- 数据不会因为重启容器丢失。

## 7. 产品经理的最佳判断框架

你不需要变成所有技术细节的专家，但要学会判断“这件事是不是靠谱”。

### 7.1 需求判断

好需求：

- 有真实用户。
- 有清晰场景。
- 有输入输出。
- 有验收标准。
- 有优先级。

坏需求：

- “做得智能一点”。
- “加个大屏”。
- “像某某产品一样”。
- “先都做上，以后再说”。

### 7.2 技术方案判断

好方案：

- 影响范围小。
- 能沿用现有架构。
- 有验证步骤。
- 有回滚方式。
- 能解释取舍。

坏方案：

- 一次改很多模块。
- 引入大量新依赖。
- 没有说明数据影响。
- 没有权限考虑。
- 只说“应该可以”。

### 7.3 AI 回答判断

可信回答通常有：

- 文件路径。
- 代码依据。
- 命令结果。
- 风险说明。
- 验证步骤。

不可信回答通常是：

- 很流畅但没有证据。
- 没读代码就给方案。
- 上来就大重构。
- 编造不存在的文件。
- 忽略你的现有环境。

### 7.4 进度判断

不要用“写了多少代码”判断进度，要用：

- 是否跑通。
- 是否可演示。
- 是否可验收。
- 是否可回滚。
- 是否有记录。

## 8. 你还需要考虑但容易忽略的层面

### 8.1 许可证和合规

开源项目不是下载了就能随便商用。要确认：

- 许可证类型。
- 是否允许商业使用。
- 是否要求开源你的修改。
- 是否有商标限制。
- 是否有企业版功能边界。

Label Studio 这类项目尤其要注意社区版和企业版边界。

### 8.2 数据安全

标注平台常处理敏感数据。要考虑：

- 数据是否能出外网。
- AI 工具是否会读取代码或数据。
- 是否包含个人信息。
- 上传文件存在哪里。
- 数据如何备份和删除。
- 日志是否泄露敏感内容。

### 8.3 成本

成本不只是服务器钱：

- 理解开源项目的成本。
- AI 调用成本。
- 构建和部署时间。
- 后续维护成本。
- 上游升级成本。
- 数据迁移成本。
- 测试成本。

最好判断：

```text
如果这个系统没人维护 3 个月，会不会坏到没人敢动？
```

### 8.4 团队协作

哪怕现在只有你一个人，也要按多人协作习惯做：

- 分支开发。
- 清晰提交。
- 需求记录。
- 决策记录。
- 部署记录。
- 账号和密钥不写进代码。

这是为了未来能交给别人。

### 8.5 可观测性

系统不是跑起来就完了，还要知道它为什么坏。

至少要能看到：

- 应用日志。
- 错误日志。
- 请求日志。
- 数据库连接问题。
- 文件上传问题。
- AI 调用失败原因。

### 8.6 备份和恢复

特别是 Docker 项目，要分清：

- 容器删了，数据还在不在。
- 镜像删了，数据还在不在。
- 数据目录在哪里。
- 数据库 volume 在哪里。

没有备份恢复方案，不要放真实数据。

### 8.7 账号、权限和审计

内部系统最容易低估权限：

- 谁能看数据。
- 谁能改数据。
- 谁能导出数据。
- 谁能删除数据。
- 谁的操作需要记录。

凡是涉及数据标注、审核、导出，都要考虑审计。

### 8.8 产品体验

AI 很容易把功能做出来，但体验粗糙。你要重点把关：

- 空状态。
- 加载状态。
- 错误提示。
- 表单校验。
- 批量操作。
- 撤销和确认。
- 导入导出说明。
- 移动端或小屏幕是否需要支持。

### 8.9 长期维护

每个系统都要回答：

- 谁维护？
- 怎么部署？
- 怎么升级？
- 怎么备份？
- 怎么排错？
- 怎么交接？
- 怎么停用？

没有维护答案的系统，越成功越危险。

## 9. 阶段交付物和过关标准

真正专业的开发，不是“想到哪改到哪”，而是每个阶段都有产物。你可以把下面这张表当作所有项目的检查清单。

| 阶段 | 关键产物 | 过关标准 |
| --- | --- | --- |
| 问题定义 | 一页纸项目说明 | 用户、场景、痛点、收益、不做范围清楚 |
| 方案选择 | 二开/从零/采购判断表 | 选择理由明确，替代方案被比较过 |
| 技术验证 | Spike 记录 | 关键风险被实际运行验证过 |
| 项目地图 | `project-map.md` | 能定位前端、后端、数据、部署 |
| 需求清单 | `requirements.md` 或需求表 | 每条需求可验收、可排序 |
| 原型设计 | 页面流程图或 HTML/Figma 原型 | 用户能从头走到尾 |
| 数据设计 | 数据模型图/表结构说明 | 核心对象和关系稳定 |
| 开发计划 | 版本路线和任务拆分 | 每个任务是可演示闭环 |
| 开发实现 | 代码改动和提交 | Git diff 可解释、无无关改动 |
| 测试验收 | 测试清单和结果 | 正常、异常、权限、数据都测过 |
| 部署上线 | 部署手册和回滚方案 | 出问题能恢复 |
| 运营维护 | 运维手册和变更记录 | 后续有人能接手 |

建议每个项目最少保留这些文档：

```text
docs/project-brief.md
docs/project-map.md
docs/requirements.md
docs/dev-runbook.md
docs/test-checklist.md
docs/deploy-runbook.md
docs/change-log.md
docs/decision-log.md
```

如果是很小的项目，可以合并成一个 `docs/project-notes.md`，但内容不能消失。

### 9.1 项目开始前的判断门

满足以下条件再开始正式开发：

- 目标用户明确。
- MVP 边界明确。
- 数据来源明确。
- 技术路线能跑通。
- 开发环境可恢复。
- 第一版验收标准明确。

不满足时，不要急着写代码，先补调研、原型或 Spike。

### 9.2 进入编码前的判断门

满足以下条件再让 AI 改代码：

- 需求已经拆成单个闭环。
- 影响页面、接口、数据、权限已经初步判断。
- AI 已读过相关文件。
- AI 已给出修改方案。
- 你知道如何验证。

### 9.3 合并或上线前的判断门

满足以下条件再合并或上线：

- Git diff 已检查。
- 核心流程已验证。
- 数据备份明确。
- 回滚方式明确。
- 日志无关键错误。
- 文档已更新。

## 10. 单个需求的日常工作流

### 阶段 0：环境隔离

目标：保证能试错，不破坏旧环境。

动作：

1. 保留原有可运行版本。
2. 源码版使用独立端口，例如 `8081` 或 `8082`。
3. 源码版使用独立数据目录，不直接复用生产数据。
4. 每次改动前确认 Git 状态干净。

验收：

- 原容器可恢复。
- 新源码目录可独立构建。
- 数据目录可删除重建。

### 阶段 1：读项目

给 AI 的任务不要说“分析一下这个项目”，要说清楚输出结构：

```text
请阅读当前项目，不要修改代码。
按以下结构输出：
1. 技术栈
2. 启动方式
3. 前端目录
4. 后端目录
5. 数据库与迁移
6. 登录认证流程
7. 核心业务流程
8. 二开风险点
9. 我作为产品经理应该优先理解的 10 个文件
```

验收：

- 能指出前端入口。
- 能指出后端入口。
- 能指出配置文件。
- 能指出 Docker 运行方式。
- 能指出核心业务模块。

### 阶段 2：跑起来

目标：从源码运行出一个可访问版本。

动作：

1. 先用项目自带 Docker 或 Docker Compose。
2. 如果 Docker 构建太慢，再考虑本地开发环境。
3. 端口和数据目录必须与旧版本隔离。
4. 记录启动命令、登录方式、常见报错。

验收：

- 浏览器可访问。
- 能注册或登录。
- 能完成最小业务流程。
- Docker 日志无关键错误。

### 阶段 3：做第一处小改动

第一处改动不要选复杂功能，建议选：

- 改登录页文字。
- 改页面标题。
- 改一个按钮文案。
- 隐藏一个不需要的入口。
- 增加一个只读展示字段。

目标不是功能价值，而是打通“定位文件 -> 修改 -> 构建 -> 运行 -> 验证”的完整链路。

验收：

- 能说清改了哪个文件。
- 能说清为什么改这个文件。
- 页面变化可见。
- 出问题能回滚。

### 阶段 4：建立需求到代码的转换模板

每个需求都按这个模板写：

```text
需求名称：
用户角色：
业务场景：
当前问题：
目标行为：
页面影响：
接口影响：
数据影响：
权限影响：
验收标准：
不做范围：
```

这个模板非常适合产品经理。它能防止 AI 只看表面页面，忽略接口、数据和权限。

### 阶段 5：让 AI 先出方案再改代码

正式改动前，让 AI 先输出：

```text
请先不要改代码。
请基于当前项目代码，给出实现方案：
1. 需要修改哪些文件
2. 每个文件为什么要改
3. 是否涉及数据库迁移
4. 是否影响已有接口
5. 是否影响权限
6. 验证步骤
7. 回滚方式
```

你确认后再让它执行。

### 阶段 6：提交与记录

每完成一个闭环，记录：

- 改动目标。
- 改动文件。
- 验证方式。
- 遗留问题。
- 下一步建议。

Git 提交信息建议：

```text
feat: add reviewer status filter
fix: correct export filename encoding
docs: add local docker runbook
refactor: simplify task list query
```

## 11. 产品经理转 AI 编码的能力模型

### 5.1 必须掌握的工程基本概念

不需要一开始就成为专业程序员，但必须理解这些概念：

- Git：分支、提交、回滚、diff、冲突。
- HTTP：请求、响应、状态码、Header、Cookie、Token。
- 前端：页面、组件、路由、状态、接口请求。
- 后端：接口、服务、模型、权限、任务。
- 数据库：表、字段、索引、迁移、外键。
- Docker：镜像、容器、端口、挂载、环境变量。
- 日志：启动日志、错误堆栈、请求日志。
- 测试：单元测试、接口测试、端到端测试。

### 5.2 最容易犯的错误

- 只描述“我要什么页面”，不描述“数据从哪来”。
- 只让 AI 改，不让 AI 解释影响范围。
- 一次改动跨太多文件。
- 不看 Git diff 就运行。
- 不保留旧环境。
- 不记录做过什么。
- 不区分“源码”“镜像”“容器”“数据目录”。
- 不知道问题发生在前端、后端、数据库还是部署层。

### 5.3 你的优势用法

你应该把产品能力转成 AI 可执行的输入：

- 把模糊想法变成用户故事。
- 把用户故事变成验收标准。
- 把验收标准变成测试步骤。
- 把业务流程变成状态流转图。
- 把页面需求变成字段、接口、权限清单。

这比直接问“帮我写代码”强很多。

## 12. 开源项目二开专项规范

### 6.1 不要直接在主分支乱改

建议：

```bash
git checkout -b feature/local-customization
```

每一类改动建一个分支：

- `feature/login-branding`
- `feature/custom-export`
- `feature/task-review-flow`
- `fix/docker-local-run`

### 6.2 不要急着升级依赖

二开早期先不要做：

- 升级 Python 大版本。
- 升级 Node 大版本。
- 大规模更新前端依赖。
- 替换数据库。
- 改构建工具。

先跑通，再理解，再小改，最后才考虑升级。

### 6.3 尊重原项目架构

优先沿用原项目已有写法：

- 原项目怎么写接口，你就怎么加接口。
- 原项目怎么做权限，你就怎么接权限。
- 原项目怎么管理状态，你就怎么扩展状态。
- 原项目怎么组织组件，你就放到同类目录。

不要让 AI 引入一套“看起来更现代”的新架构，除非你明确要重构。

### 6.4 二开必须记录与上游的关系

开源项目会更新。你的二开版本要知道：

- 基于哪个上游提交。
- 改了哪些文件。
- 哪些改动以后可能与上游冲突。
- 是否需要定期合并上游更新。

建议保留：

```bash
git remote -v
git log --oneline -5
git diff develop...你的分支
```

## 13. AI 提示词模板

### 7.1 读代码模板

```text
你是资深工程师，请阅读当前仓库。
不要修改文件。
请按“业务模块 -> 关键文件 -> 数据流 -> 风险点”的方式解释。
我不是专业程序员，请用产品经理能理解的话说明，但保留必要技术术语。
```

### 7.2 定位功能模板

```text
请帮我定位“某某功能”的代码。
要求：
1. 先列出可能相关的前端文件
2. 再列出可能相关的后端文件
3. 说明页面如何调用接口
4. 说明数据最终存在哪里
5. 不要修改代码
```

### 7.3 改代码前方案模板

```text
我想实现以下需求：
【粘贴需求】

请先不要改代码。
请给出实现方案：
1. 影响范围
2. 修改文件
3. 数据库是否变化
4. 权限是否变化
5. 可能风险
6. 验证步骤
```

### 7.4 执行改动模板

```text
按刚才确认的方案执行。
要求：
1. 每次只改必要文件
2. 保持项目原有代码风格
3. 不做无关重构
4. 修改后运行可行的验证命令
5. 最后说明改了什么、怎么验证、还有什么风险
```

### 7.5 报错修复模板

```text
这是运行报错：
【粘贴完整报错】

请判断：
1. 报错属于环境、依赖、前端、后端、数据库还是配置问题
2. 最可能原因
3. 最小修复方案
4. 是否会影响已有功能
5. 修复后如何验证
```

### 7.6 代码审查模板

```text
请以代码审查方式检查当前改动。
重点看：
1. 是否有功能 bug
2. 是否破坏已有流程
3. 是否有权限或数据安全风险
4. 是否缺少测试
5. 是否有不必要的大改
请按严重程度排序。
```

## 14. 质量门禁

每次改动完成前，至少过这张表：

| 检查项 | 必须回答 |
| --- | --- |
| 需求是否清楚 | 用户是谁，场景是什么 |
| 改动是否收敛 | 有没有无关文件变化 |
| 页面是否验证 | 是否亲自打开看过 |
| 接口是否验证 | 是否请求成功 |
| 数据是否验证 | 是否写入或读取正确 |
| 权限是否验证 | 不同角色是否受影响 |
| 日志是否正常 | 是否有关键错误 |
| 回滚是否明确 | 出问题怎么撤回 |

高级一点再补：

- 单元测试。
- 接口测试。
- 端到端测试。
- 静态检查。
- Docker 构建验证。
- PR 审查。

## 16. 30 天学习和实战路线

### 第 1 周：环境和项目地图

目标：

- 能分清源码、镜像、容器、数据目录。
- 能跑起源码版。
- 能让 AI 解释项目结构。
- 能看懂 Git diff。

产出：

- `project-map.md`
- `dev-runbook.md`
- 第一个 UI 小改动

### 第 2 周：前端小改

目标：

- 能定位页面和组件。
- 能改文案、按钮、简单展示字段。
- 能理解前端如何请求后端接口。

产出：

- 2-3 个前端小需求。
- 每个需求都有验收记录。

### 第 3 周：后端接口和数据

目标：

- 能定位接口。
- 能理解核心数据模型。
- 能做一个简单接口字段扩展或导出逻辑调整。

产出：

- 数据模型地图。
- 一个后端小需求。

### 第 4 周：形成二开节奏

目标：

- 每个需求都能按模板描述。
- 每次改动都能分支、提交、验证。
- 能让 AI 做 code review。
- 能自己判断 AI 方案是否靠谱。

产出：

- 二开需求池。
- 版本计划。
- 改动记录。

## 17. 推荐的最小工具组合

个人起步版：

- Codex：主力读代码、改代码、跑验证。
- VS Code 或 Cursor：日常看代码。

进阶协作版：

- GitHub Issues：管理需求。

- CodeRabbit 或 Copilot Code Review：辅助审查。
- Linear/Jira：管理产品任务。
- Notion/飞书文档：沉淀需求和决策。

开源/可控优先版：

- Continue CLI/插件：开源 AI coding agent，可作为研究和自建工具链参考。
- 本地模型 + Continue/Ollama：适合数据不方便外发的场景，但效果、速度和维护成本要单独评估。

## 18. 关键风险

### 12.1 数据风险

不要直接拿真实生产数据做实验。尤其是标注平台，可能包含原始文本、图片、音频、个人信息或业务敏感数据。

### 12.2 权限风险

凡是涉及登录、用户、角色、组织、项目权限的改动，都必须单独验证。

### 12.3 升级风险

开源项目依赖复杂，随意升级依赖可能导致构建失败或隐藏 bug。二开早期以“少动依赖”为原则。

### 12.4 AI 幻觉风险

AI 可能会编造不存在的文件、命令、配置项。判断标准永远是：

- 文件是否真实存在。
- 命令是否真实运行。
- 页面是否真实变化。
- 测试是否真实通过。

## 20. 最终工作口径

以后做任何二开任务，都按这个顺序：

```text
说清需求
-> 定义验收
-> AI 读代码定位
-> AI 先出方案
-> 人确认范围
-> AI 小步改代码
-> 运行验证
-> 代码审查
-> 记录决策
-> 提交版本
```

你的目标不是马上变成传统程序员，而是成为一个能用 AI 管住工程复杂度的产品型开发者。
